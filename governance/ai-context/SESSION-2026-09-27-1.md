### What the rebuild/reinstall surfaced (kept — the real lesson)

**Installing the package broke the app, and not for the reason expected.**
The user reported the app no longer working. The cause was *not* the new
code: the installer had **overwritten the working Start Menu shortcut**.
`UdiFy.lnk` pointed at `.venv\Scripts\pythonw.exe` — a trusted, signed
binary that Smart App Control allows — and the installer replaced it with
one pointing at the unsigned PyInstaller `app\UdiFy.exe`, which this
machine blocks outright. So the app was fine; its launcher was gone.

That is a serious, repeatable regression: **every future install would
re-break the only working launch path.** Recorded so it is not repeated.

Also worth keeping: a *fresh* install previously shipped no `.env` at all,
and `load_dotenv` fails silently, so a new install would quietly run in
MOCK mode looking like success. The installer fixed that; the underlying
guard (a warning when `.env` is absent, in `settings.py`) was **kept**,
since it is not installer-specific.

Two installer-authoring bugs found by testing rather than assumption: a
docstring containing `data\` was an invalid Python escape (hard
`SyntaxError`, caught at build time), and a stale Inno `/DIR=` persisted in
the registry silently redirected installs to a throwaway temp directory,
which invalidated an earlier "re-install preserves your config" test until
caught.

### What was removed

`installer.spec`, `installer-onefile.spec`, `installer.iss`, `dist\`,
`dist_installer\`, `build\`, both `.exe`s. `.gitignore`'s packaging section
removed with an explanatory note. `settings.py` reverted (the install-root
marker and `data\` audit-DB folder existed only for the install root). The
app was uninstalled via its own uninstaller — which correctly removed
program files and left real data alone — and the leftover directory removed
after verifying a backup. `UdiFy.lnk` restored to the `pythonw.exe` form.

**Standing instruction: do not reintroduce packaging** without solving code
signing or obtaining a Smart App Control exception. No packaging target can
produce a launchable binary on this machine, so it is dead configuration
that also carries the launcher-overwrite regression above.

### Two real bugs the launch itself exposed (both kept)

1. **`run_udify.py` could not import its own package when launched directly.**
   It did a bare `from src.app.main import main` with no path setup, so it
   only ever worked under pytest (which puts the rootdir on `sys.path`).
   Launched as the app actually is — `pythonw.exe run_udify.py` — it raised
   `ModuleNotFoundError` with **no console to display it**, so the app
   simply never appeared. Fixed by inserting the project root on
   `sys.path` before importing.

2. **Misleading symptom during diagnosis.** `Get-Process ... .MainWindowTitle`
   returns a *blank* title for a `pythonw` process that has not finished
   creating its window, and reading the wrong PID made a working app look
   dead twice. The reliable check is to enumerate all `pythonw` processes
   and select the one whose title is non-empty. Worth remembering before
   concluding "the app is broken" from a single PID's title.

**Evidence the app genuinely works in LIVE mode**: 400 real students load
from the school's OGR register in ~5s, and the GUI reaches
`window.show()` ~6.7s after launch.

### 1. The routing defect — fixed

`list_students()` now resolves `udise_row`/`pen_row`. Strategy derived from
read-only analysis, not assumption:

- **Aadhaar first.** Established that UDISE and PEN hold the *same* 65
  distinct Aadhaar values (sets exactly equal), so Aadhaar is a reliable
  cross-sheet key.
- **Then a DOB + class + name-subset bridge**, because OGR's AADHAR column
  is only 211/401 usable — the rest blank or `-`/`NA`. Each element exists
  for a reason found in the data: DOB because the sheets disagree on
  separator (`DD-MM-YYYY` vs `DD/MM/YYYY`); class because the vocabularies
  genuinely differ (`BALVATIKA` vs `Balvatika`, `1` vs `1st`); name-subset
  because OGR carries the full name while UDISE often carries only the
  given name.
- **Ambiguity never guessed** — two candidate rows means unresolved, for
  manual review.

**Two real bugs, both caught only by running against live data:**

1. **The class signature was case-sensitive.** Built from the raw string,
   `BALVATIKA` → `B9` but `Balvatika` → `B8`, so the vocabularies could
   never meet and the bridge matched **nothing**. A silent total failure
   that looked like "the data doesn't match" rather than "my code is
   wrong".
2. **HTTP 429 rate limiting.** The resolver made several hundred API calls.

### 2. Row-colour reads — fixed (a genuine live-run blocker)

`get_row_color()` was two API calls per row; 40 students exceeded the
60-req/min quota and returned **429**. A 429 means the app cannot tell
whether a row is already GREEN — precisely the state it must never guess.
Now one batched grids call per tab, cached, with `set_row_color()` updating
the cache so a just-written colour is never read stale.

**Verified: 401 students, 0 errors, 0 rate-limit failures, 3.2s.**

### 3. Spreadsheet-write recovery — built and wired into all 4 branches

The dangerous shape: portal work already banked, sheet write failed. Naive
recovery re-runs the workflow and can create a **second real student
record**. So `recover_sheet_write()` takes **no portal adapter** — it is
*structurally* incapable of repeating the action, which a test asserts.
Verifies before writing, retries the sheet, then escalates with a message
that says explicitly **"do not re-run"**, plus an auditable
`PEN_SPREADSHEET_UPDATE_FAILED` event.

Used the project's existing typed event path rather than a raw string —
the first attempt passed `event_code` as a string and failed with
`'str' object has no attribute 'value'`, because `EventCode` is an enum.
